## 2. 設計內容

### 2.1 函式介面

```c
uint32_t rotl_ref(uint32_t rs1, uint32_t rs2);
```

| 決策 | 原因 |
|---|---|
| 參數與回傳值都用 `uint32_t` | 旋轉是位元操作,不需要正負號。無號數的 `>>` 一定是**邏輯右移**(左邊補 0)。若用 `int32_t`,負數右移在 C11 是 implementation-defined,GCC / Clang 會做算術右移(補 1),結果錯誤 |
| `rs2` 也用 `uint32_t`,函式內取 `rs2 & 31` | 規格只用 `rs2` 的低 5 位元。`rs2 = −1` 傳進來是 `0xFFFFFFFF`,取低 5 位元後為 31,與規格一致 |
| `n == 0` 單獨回傳 `rs1` | 照公式計算會得到 `rs1 >> 32`。C11 §6.5.7 規定移位量大於等於型別寬度是**未定義行為**,編譯器可以產生任何結果 |

### 2.2 實作

```c
uint32_t rotl_ref(uint32_t rs1, uint32_t rs2)
{
    uint32_t n = rs2 & 31u;
    if (n == 0)
        return rs1;
    return (rs1 << n) | (rs1 >> (32u - n));
}
```

原始碼:[`src/c_baseline/rotl.c`](../src/c_baseline/rotl.c)

**反例**(`make ub-demo`):把 `n == 0` 的分支拿掉,`n = 4` 時結果正確,`n = 0` 時 UBSan 回報:

```
runtime error: shift exponent 32 is too large for 32-bit type 'uint32_t'
```

RISC-V 和 x86 的移位硬體都只取移位量的低 5 位元,`x >> 32` 在硬體上會變成 `x >> 0`,結果 `x | x = x` 看起來剛好正確。但在 C 語言層級這是未定義行為,編譯器最佳化時可以假設它不會發生,所以不能依賴「剛好算對」。

**假設**:`uint32_t` 為 32 位元;主機與 RISC-V 目標皆為二補數。

### 3.1 5 Whys 推理鏈

我們要回答的決策是:`rotl_ref` 為什麼不讓公式直接算,而要先把 `n == 0` 挑出來?下面每一層都附上我們實際查過或跑過的證據。

| 層 | 為什麼? | 答案 | 驗證方式 |
|---|---|---|---|
| 1 | 為什麼要先把 `n == 0` 挑出來? | 因為公式右半是 `rs1 >> (32 − n)`;`n = 0` 時就是 `rs1 >> 32`。這已經不是「轉 0 格」,而是要求一個 32 位元的數右移 32 位 | 把 `n = 0` 代入公式手算;T02(`rs2 = 0`)與 T05(`rs2 = 32`,取低 5 位後 `n = 0`)都是這個情況 |
| 2 | 為什麼 `rs1 >> 32` 不能直接寫? | C11 規定:移位量若大於等於型別寬度,行為未定義。`rs1` 是 32 位元,所以 32 已經越界;編譯器沒有義務給出任何特定結果 | C11(N1570)§6.5.7 第 3 段;`make ub-demo` 在 `n = 0` 時,UBSan 印出 `shift exponent 32 is too large for 32-bit type` |
| 3 | 為什麼在我們的電腦上「看起來是對的」還不算過關? | 因為那是硬體幫忙掩蓋了錯誤:CPU 的移位只採計移位量的低 5 位元,32 的低 5 位元是 0,所以機器實際做的是 `rs1 >> 0`,剛好等於原值。但 C 標準看的是原始碼,不是這顆 CPU 的實作;換編譯器或開最佳化,結果就可能不同 | 用 `cc -std=c11 -O0` 與 `-O2` 各編一次 `ub_demo.c`,執行 `./a.out 0` 都印出 `0x12345678`;C11 §3.4.3 對未定義行為的說明 |
| 4 | 為什麼我們不接受「在這台電腦上是對的」? | 因為 `rotl_ref` 的角色是標準答案,不是一次性的實驗。同一份程式必須在 clang、GCC、不同最佳化等級,以及之後的 RISC-V 編譯器上都給出同一個結果,否則後面的比對就沒有意義 | `Makefile` 的 `test-c` 用 `-O2`;`make test-ubsan` 用同一組測資檢查 `rotl_ref` 沒有未定義行為 |
| 5 | 為什麼標準答案一定要這麼嚴格? | 因為後面的手寫組合語言、自訂指令與模擬器,全部都要拿 `rotl_ref` 的輸出當基準。基準只要有一個情況不確定,後面所有「通過」都可能是巧合 | `make test-c`:16 組測資全過;另外與「每次只旋 1 位」的獨立寫法比對 1000 × 69 = 69,000 次,全部一致 |

結論:把 `n == 0` 獨立處理,不是為了讓某台機器跑得對,而是讓這段 C 程式在語言層級就沒有不確定的地方。我們的理解是:參考實作的可信度,來自「每個輸入都有定義」,而不是「這次跑出來剛好一樣」。

## 4. 遭遇的問題與解法

**問題:反例測試明明「通過」了,畫面卻像建置失敗。** 第一次在組員的 Mac(Apple clang 21,arm64)跑 `make ub-demo`,最後出現 `make: *** [ub-demo] Abort trap: 6`,當下以為是程式或 Makefile 壞了。回頭看 `echo $?`,make 的結束碼卻是 0,兩件事互相矛盾。

**追查:** 對照 `Makefile` 才發現,執行反例的那一行寫成 `-./build/ub_demo 0`。前面的 `-` 是 make 的語法,意思是「這一行失敗也繼續」;而 `ub_demo` 是用 `-fno-sanitize-recover=all` 編的,UBSan 一抓到「移位 32」就讓程式中止,所以作業系統回報 Abort trap: 6。也就是說,這個中斷是我們**故意**要它發生的,不是建置錯誤。

**我們的理解:** 這裡要分清楚「預期失敗」和「壞掉」。如果只看最後一行,會以為工具鏈有問題;但把結束碼、Makefile 的 `-` 與 UBSan 的設定一起看,就會知道這是反例成功的證據。反過來說,把 `ub_demo.c` 拿掉 sanitizer 再編一次,`n = 0` 時照樣印出 `0x12345678`,完全看不出異狀——這正是為什麼 `make test` 不能只跑一般測試,還要另外跑 `test-ubsan`。程式本身不需要修改,需要改的是我們對這行訊息的解讀。

## 5. 白話說明

把 32 位元的數字想成一個 32 格的圓環,ROTL 就是往左轉 n 格,轉出左邊的會從右邊接回來。程式用「左移 n 格」和「右移 32−n 格」拼出這個效果。我們卡住的是轉 0 格:照公式要右移 32 格,但 C 語言沒規定這件事的結果。不開檢查工具時,錯誤寫法在我們的電腦上剛好算對,看起來完全沒問題;開了 UBSan 才發現它其實是未定義行為。修正方式是一開始就判斷:轉 0 格直接回傳原值,讓每個輸入都有明確結果。
