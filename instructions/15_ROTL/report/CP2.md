# CP2:RV32IM 實作

## 1. 本次目標

只用 RV32IM 指令實作 `ROTL`,並統計靜態與動態指令數、分支數。

> **繳交範圍**:CP2 的評分內容是版本 A(2.2)、版本 B(2.3)與 RV32IM 的指令統計。`rotl.S` 中的 `rotl_custom`、`spec/rotl_isa.h` 以及表格中「自訂指令」的欄位屬於 CP3,funct3 / funct7 依課程公告為 000 / 0000000,在本報告只作為對照。

## 2. 設計內容

### 2.1 呼叫慣例

依 ilp32 ABI:`a0 = rs1`、`a1 = rs2`,結果放 `a0`。函式只用 caller-saved 暫存器(`t0`–`t2`),不呼叫其他函式,所以不需要存取堆疊。

### 2.2 版本 A:逐字翻譯(含分支)

```asm
rotl_branch:
    andi    a1, a1, 31          # n = rs2 & 31
    beqz    a1, 1f              # n == 0 -> rd = rs1
    li      t0, 32
    sub     t0, t0, a1          # t0 = 32 - n
    sll     t1, a0, a1          # t1 = rs1 << n
    srl     t2, a0, t0          # t2 = rs1 >> (32 - n)
    or      a0, t1, t2
1:
    ret
```

與 C 參考實作一一對應,`n = 0` 用分支跳過。

### 2.3 版本 B:無分支

```asm
rotl_branchless:
    sll     t0, a0, a1          # rs1 << (rs2 & 31)
    neg     t1, a1              # -rs2
    srl     t1, a0, t1          # rs1 >> ((-rs2) & 31)
    or      a0, t0, t1
    ret
```

這個版本利用 RV32I 的一個特性:**`sll` / `srl` 只取 `rs2` 的低 5 位元**(規格書 RV32I 章節)。因此:

| `n = rs2 & 31` | `sll` 實際移位 | `(−rs2) & 31` = `srl` 實際移位 | 結果 |
|---:|---:|---:|---|
| 0 | 0 | 0 | `rs1 \| rs1 = rs1` ✓ |
| 1 | 1 | 31 | `(rs1 << 1) \| (rs1 >> 31)` ✓ |
| 8 | 8 | 24 | `(rs1 << 8) \| (rs1 >> 24)` ✓ |
| 31 | 31 | 1 | `(rs1 << 31) \| (rs1 >> 1)` ✓ |

- 不需要 `andi`:硬體本來就只看低 5 位元
- 不需要 `n = 0` 的分支:`n = 0` 時兩邊都移 0 位,`rs1 | rs1` 還是 `rs1`
- C 語言不能這樣寫(`x >> 32` 是未定義行為),但組合語言可以,因為硬體行為是明確定義的

### 2.4 編譯器輸出(GCC 16.2.0)

`make asm` 產生 `build/rotl_O0.s` 與 `build/rotl_O2.s`。`-O2` 的結果:

```asm
rotl_ref:
    andi    a1,a1,31
    neg     a5,a1
    srl     a5,a0,a5
    sll     a0,a0,a1
    or      a0,a5,a0
    ret
```

- GCC 認得這是旋轉,**自動消除了 `n = 0` 的分支**,做法與版本 B 相同
- 但保留了一條多餘的 `andi`,所以比版本 B 多 1 條
- `-O0` 的版本有 26 條指令,包含堆疊存取與分支

### 2.5 旋轉量為常數時

ChaCha20 的旋轉量固定為 16、12、8、7,不需要計算 `32 − n`,GCC 產生 3 條。以單獨編譯 `(x << 7) | (x >> 25)` 為例:

```asm
    srli    a5,a0,25
    slli    a0,a0,7
    add     a0,a0,a5     # 兩半的位元不重疊,所以 add 與 or 結果相同
```

在 ChaCha20 中,這三條會與其他 quarter round 的指令交錯排列。

### 2.6 量測方法

| 項目 | 說明 |
|---|---|
| 計數方式 | **靜態**:函式在執行檔中的指令條數。**動態**:實際執行的指令條數 |
| 編譯器 | `riscv64-elf-gcc (GCC) 16.2.0`,`-march=rv32im -mabi=ilp32 -O2 -ffreestanding` |
| 模擬器 | 本組的 Python RV32IM 指令集模擬器 [`tools/rv32sim.py`](../tools/rv32sim.py)(Python 3.14.8) |
| 歸屬規則 | 函式指令數包含 `ret`,不含呼叫端的 `call`;被呼叫函式的指令算在呼叫者內(包含式) |
| 正確性 | 每次量測都把輸出與 Python 黃金模型比對,ChaCha20 與 RC5 另與公開測試向量比對,不一致就中止 |

模擬器只計算指令數,不模擬 pipeline。`rv32sim.py` 是模擬器模組,由 `test_rv32.py` 與 `measure.py` 匯入,沒有獨立的執行入口;要跑模擬器上的驗證與量測,請用 `make test-py` 與 `make counts`。

`li`、`neg`、`beqz`、`ret` 是組合語言的**偽指令**,組譯後各對應 1 條真實指令(`addi`、`sub`、`beq`、`jalr`)。表中的指令數是模擬器實際執行的機器指令,所以已經是展開後的數字。

執行證據:由組員執行 `make evidence ID=<學號>`,完整輸出存在 `report/figures/run_log_<學號>.txt`。

## 3. 結果與分析

以下數字由 `make counts` 產生,完整表格見 [`figures/instruction_counts.md`](figures/instruction_counts.md)。

### 3.1 單一 ROTL 函式(16 組測資)

| 版本 | 靜態指令數 | 靜態分支數 | 動態指令數(n = 0) | 動態指令數(n ≠ 0) | 16 組總數 | 動態分支(taken) |
|---|---:|---:|---:|---:|---:|---:|
| 版本 A:逐字翻譯 | 8 | 1 | 3 | 8 | 118 | 16(2) |
| 版本 B:無分支 | 5 | 0 | 5 | 5 | 80 | 0(0) |
| C 參考實作,GCC `-O2` | 6 | 0 | 6 | 6 | 96 | 0(0) |

(皆含 `ret`。)

- 版本 A 只有在 `n = 0` 時較快。16 組測資中有 2 組 `n = 0`(T02、T05),所以 taken 為 2
- 若 `n` 均勻分布在 0–31,版本 A 平均為 3 × 1/32 + 8 × 31/32 ≈ 7.84 條,版本 B 固定 5 條(皆含 `ret`;只算旋轉本身則 B 為 4 條,見 [`spec/README.md`](../spec/README.md))
- 版本 A 的分支在之後學到 pipeline 時還會帶來 control hazard。版本 B 沒有分支,動態指令數也固定

### 3.2 實際程式中的旋轉(RV32IM 基準)

用兩個使用循環左移的密碼學核心(皆以 GCC `-O2` 編譯,各執行一次):

| 核心 | 旋轉種類 | 旋轉次數 | 靜態指令數 | 動態指令數 | 動態分支數 |
|---|---|---:|---:|---:|---:|
| ChaCha20 區塊函式 | 常數(16、12、8、7) | 320 | 236 | 1919 | 42 |
| RC5 金鑰排程 | 常數 3 + 變數 | 156 | 62 | 2467 | 103 |
| RC5 加密一個區塊 | 變數(由資料決定) | 24 | 29 | 227 | 12 |

動態指令組成(節錄自表 3):

- ChaCha20:`slli` 320 次、`srli` 320 次,正好每次旋轉各一條;合併兩半的 `add` 也是 320 次
- RC5 加密:`sll`、`srl`、`or`、`andi`、`neg` 各 24 次,即每次變數旋轉 5 條,與 2.4 節的編譯器輸出相同

分支數只來自迴圈。ChaCha20 有 16 + 10 + 16 = 42 次,對應複製狀態、10 次 double round、輸出相加三個迴圈。旋轉本身沒有分支。

### 3.3 5 Whys 推理鏈

決策:為什麼最後選無分支的版本 B,而不是照 C 程式逐字翻成版本 A?我們把理由拆成五層,每層都對回量測或規格。

| 層 | 為什麼? | 答案 | 驗證方式 |
|---|---|---|---|
| 1 | 為什麼不選版本 A? | A 在 `n ≠ 0` 時要跑 8 條,只有 `n = 0` 時才是 3 條;B 不論 `n` 是多少都固定 5 條(都含 `ret`)。把 `n` 當成 0–31 均勻分布,A 的平均是 3 × 1/32 + 8 × 31/32 ≈ 7.84 條,還是比 B 多 | `make counts` 表 1:A 動態 3 / 8、16 組總數 118;B 固定 5、總數 80 |
| 2 | 為什麼 B 可以省掉 `andi` 與 `n = 0` 的判斷? | 因為 RV32I 的 `sll` / `srl` 在硬體上只取 `rs2` 的低 5 位元,等於免費做了 `& 31`;既然移位量一定落在 0–31,就不需要再遮一次,也不需要為 0 開岔路 | RISC-V 手冊 §2.4;`tools/test_rv32.py` 的 `test_shift_uses_low_five_bits` |
| 3 | 為什麼 `n = 0` 時 B 也不會出錯? | `n = 0` 時左半 `sll` 移 0 位;`neg` 得到 0,`srl` 也移 0 位,兩半都是原值,`or` 起來還是原值。也就是說,B 不是「忽略 0」,而是 0 本來就被公式涵蓋 | 手算;`test_branchless_version` 在 380 組輸入(含 `rs2 = 0`、`32`)上與黃金模型一致 |
| 4 | 為什麼 CP1 的 C 版本要判斷 0,組合語言卻不用? | 因為兩邊的規則不同:C 標準說移位量 ≥ 32 是未定義行為,程式設計者必須自己避開;RV32I 則明文規定只看低 5 位元,硬體結果有保證。我們在 C 裡避開的是語言層級的未定義,不是硬體會出錯 | C11 §6.5.7;CP1 的 `make ub-demo`;RISC-V 手冊 §2.4 |
| 5 | 除了少幾條指令,無分支還有什麼好處? | 動態指令數固定,不會因為資料不同而忽快忽慢;而且沒有岔路,之後學 pipeline 時就不會遇到 control hazard。對密碼學核心來說,執行時間也比較好預測 | 表 1:A 動態分支 16 次(taken 2 次),B 為 0 |

結論:版本 B 不是「把 C 硬翻成組合語言」,而是利用 RV32I 已定義好的移位行為,把 `& 31` 與 `n = 0` 的判斷一起省掉。我們的理解是:組合語言的最佳化,往往來自「規格已經保證的事」,而不是多寫幾條檢查。

## 4. 遭遇的問題與解法

**問題:準備 Demo 時直接執行 `python3 tools/rv32sim.py`,畫面沒有任何輸出。** 我們原本以為它會跑完所有測試,但在 Mac 上實際執行時,程式不到一秒就結束,結束碼是 0。打開原始碼才發現 `rv32sim.py` 沒有 `if __name__ == "__main__"`:它只是被 `test_rv32.py` 和 `measure.py` 匯入的模擬器模組,單獨執行只會載入定義,不會跑測試。

**追查:先確認這支程式該怎麼用,也把兩套驗證的範圍分清楚。** `make test-py` 才是模擬器上的測試入口;69,000 次是 CP1 的 C 參考實作與逐位旋轉的交叉比對,模擬器上的測試則是 `test_rv32.py` 用 380 組輸入比對四個版本。兩者範圍不同,不能互相代替。

**解法:改用 `make test-py` 與 `make counts`。** 兩者在 Mac 上執行都通過,產生的表格與本報告一致。這件事讓我們學到:程式沒有輸出不代表成功,要先確認它的入口與適用範圍;報告裡的數字也要註明是哪一套驗證產生的。

## 5. 白話說明

把 32 位元想成 32 格的圓環。版本 A 每次先問「要轉 0 格嗎?」是就結束,不是才分左右兩半。版本 B 不問,直接轉:左半往左、右半往右,再接起來。因為圓環只有 32 格,轉 32 格等於繞回原點;CPU 搬位元時只看「轉幾格」的最後 5 個位元,32 的最後 5 位是 00000,對它來說就是 0 格。卡住的是:CP1 的 C 程式一定要先判斷 0,便以為組合語言也一樣;後來查到 CPU 說明書有明確定義,才放心拿掉判斷,每次固定 4 步。
